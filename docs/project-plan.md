# 팬덤 총대 에이전트 — 기획

> 출처: Notion "팬덤 총대 에이전트 — 해커톤 기획" (2026-07-25 최종 수정, 2026-07-28 스냅샷)
> API 목록은 [api-spec.md](api-spec.md) 참조.

팬덤 **총대**가 생일카페·지하철광고 등 그룹 프로젝트를 위해 수천만 원을 걷어 집행하는 과정에서 발생하는 **먹튀(자금 유용)를 방지**하는 에스크로·투명성 시스템. Solana 기반 자금 보관 + AI 정책 판단 에이전트로 지출을 검증한다.

해커톤 제출용 — 심사 항목 5개 + 가산점 2개 기준으로 작성됨.

## 1. AI 활용도 (Gemini / Vertex AI)

**결제 정책 관리 에이전트** — 캠페인 정책·잔액·증빙을 입력받아 지출의 정당성을 판단한다.

| | |
|---|---|
| **입력** | 캠페인 정책(지하철 광고 / 생일 카페 등), 잔액(Solana 지갑), 견적서·영수증(벤더 제출 증빙), 벤더 대금 지급 요청 |
| **판단** | 목표·마감 충족 여부 / 카테고리·단가·총액 / 벤더 allowlist / 증빙↔지출 매칭 |
| **출력** | 필요 금액 산정(얼마가 더 필요한지), 기간 내 목표 미달 시 환불 처리 |

## 2. Solana 온체인 구현 (USDC · Solana Pay · pay.sh)

모금 → 보관 → 집행/환불 전 과정을 온체인에서 처리해 투명성을 확보한다.

- **모금** — Solana Pay QR/딥링크로 기여자가 USDC 전송 → escrow PDA 입금. 각 기여자의 기여액·원금 비율을 온체인 기록
- **에스크로 (Anchor 프로그램)** — `create_campaign`(정책·목표·마감 생성) / `contribute`(기여자 USDC 입금) / `release`(집행 대금 지급) / `refund`(환불)
- **집행** — 에이전트가 allowlisted 벤더에게 USDC transfer
- **환불** — 기여자 비율·원금 기록 기반 일괄 환불 (온체인 기록 활용)
- **pay.sh** — 에이전트가 Gemini·외부 API 호출 비용을 스테이블코인으로 micropay

> USDC · Solana Pay · pay.sh 세 가지는 **요강 필수 온체인 스택**.

## 3. GCP 아키텍처 & 프로토콜 연동

- **서버(백엔드+에이전트)** — `docker compose` 기반, 개인 서버에서 개발·테스트 → 제출 시점에 **GCP Cloud Run으로 이전**(심사 대상). Cloud Run은 단일 컨테이너 단위라 이전 시 서비스별 분리 필요 (또는 GCE VM에 compose 유지)
- **웹** — 개인 서버 배포 (필요 시 GCP로 통일)
- **앱** — 별도 클라이언트 ← **이 레포**
- **프로토콜** — AP2(Agent Payments Protocol) / x402 결제 프로토콜 연동

## 4. 상업성 & 기관 적용성 + UX & 혁신성

**상업성**

- 타깃 — 팬덤 플랫폼 / 이벤트 마켓플레이스 등 다수의 소액을 모아 집행("원기옥")하는 곳
- 문제 — 오프체인 모금 시 총대 먹튀, 정산 분쟁
- 수익 모델 — 캠페인당 수수료 / 기관 대상 SaaS / (선택) 에스크로 예치금 플로트 이자 *(전자금융·신탁 규제 검토 필요)*

**UX & 혁신성 — 핵심 혁신: 총대의 "집행 버튼"을 없앤다**

총대가 자금을 쥐고 재량으로 집행하는 구조 → 에이전트가 정책대로 자율 집행하고 총대는 상태만 관리하는 구조로 전환. *"신뢰하는 사람"을 "검증하는 프로토콜"로.*

- **팬 관점** — 지갑 연결 **또는 Passkey + 임베디드 지갑**. 가스비는 feepayer / sponsored tx(**gasless**) → 크립토 몰라도 참여 가능
- **총대 관점** — 집행 버튼 제거 → **에이전트 상태 대시보드** 관리만. 에이전트가 정책 기반으로 자율 처리

## 가산점 1. A2A 멀티 에이전트

한 캠페인을 **역할 분담한 4개 에이전트 크루**가 A2A(Agent2Agent) 프로토콜로 소통하며 협업 운영한다.

| 에이전트 | 역할 | 관련 API |
|---|---|---|
| 오케스트레이터 / 정책 | 캠페인 정책 보유, 전체 조율 | `POST /agent/policy/evaluate` |
| 벤더 협상 | 벤더 측 에이전트와 A2A로 견적 제출·대조·자동 협상/승인 (사람 개입 없는 조달 파이프라인) | `POST /agent/negotiate`, `POST /agent/a2a/message` |
| 검증 / 감사 | 증빙↔지출 매칭, allowlist 대조 | `POST /agent/audit`, `POST /proof/{id}/verify` |
| 정산 / 환불 | 기여 비율 계산 → release / refund 온체인 트리거 | `POST /settlement/{campaignId}/release`·`/refund` |

## 가산점 2. Solana 네이티브 심화

- **SPL / cNFT** — 기여자에게 **기여 증서(cNFT)** 발행 → 팬이 캠페인 참여 증표를 지갑에 소장
- **SendAI (Solana Agent Kit)** — 에이전트의 온체인 액션 실행 툴킷 *(활용 방식 검토 중)*
- **Seed Vault / Solana Mobile** — *(시간 되면)* 모바일 서명 지원

## 앱 관점 정리

기획상 앱에는 최소 두 개의 사용자 역할이 있다.

**팬** — Passkey 온보딩 → 캠페인 탐색 → Solana Pay로 USDC 기여 → 기여 내역·cNFT 증서 확인
관련: `/auth/passkey/*`, `/campaign`, `/payment/solana-pay/*`, `/users/me/contributions`, `/users/me/certificates`

**총대** — 캠페인 생성 → 벤더·견적 관리 → **에이전트 상태 대시보드**(집행 버튼 없음) → 정산·마감
관련: `POST /campaign`, `/vendor/*`, `/agent/status`, `/agent/{campaignId}/decisions`, `/settlement/*`

### 리스크

- 팬 온보딩의 핵심인 `/auth/passkey/*`, `/auth/wallet/*`가 서버에서 **전부 "시작 전"**
- `/proof` 그룹 6개 전부 "시작 전" — 증빙 업로드·검증 플로우 미구현
- **화면 정의·플로우 문서가 아직 없음** → 라우팅·화면 설계 착수 불가
- 요청/응답 스키마 미확보 → 모델 클래스 작성 불가
